## 1. Product Overview

**Name:** Hamsayaa (ہمسایہ — "neighbor")

**One-liner:** A WhatsApp AI concierge for gated communities and apartment societies, paired with a real-time admin dashboard. Residents get instant answers, visitor passes, and bill tracking with zero app installation; admins get unified operational control for complaints, gate logs, dues, and polling.

**Problem Solved:** Gated communities operate on fragmented WhatsApp groups, paper registers, and manual bookkeeping. Complaints get lost, admins have zero visibility into vehicle overstays, and dues collection is inefficient and error-prone.

**Target Market:** Gated communities and apartment societies, launching in Karachi, Pakistan.
**Founders:** Absar Anwer, Hateem, Ahmed.
**Revenue Model:** Hamsayaa bills the **society directly** each month on a per-unit/apartment basis. The subscription rate is **admin-configurable per society**. The resident receives a monthly cumulative bill with an itemized breakdown (society maintenance fee, utility charges, Hamsayaa SaaS fee), but payment is made to the **society's own account**. Hamsayaa's revenue is decoupled from whether individual residents pay or not — if a society has subscribed for X units, Hamsayaa charges the society cumulatively for those X units each month.

> **Note:** The resident bill is generated by the Admin each cycle (not a fully automatic recurring charge), and the Admin is allowed to make changes to resident bills directly.

## 2. Stakeholders & Roles

| Role | Description | Primary Interface |
|---|---|---|
| **Resident** | Owner or tenant residing in a unit | WhatsApp only |
| **Admin** | Day-to-day operational staff (office manager, building supervisor) | Web dashboard |

> **Security & Gatekeeper Policy:** Security guards and gate staff have **no login credentials, system access, or WhatsApp bot interaction**. Gate staff records exist purely in the Employee Directory (see Section 3.2, item 6). Vehicle entries and visitor passes are managed via manual Admin entry, Excel batch imports, or automated camera inputs (Phase 2).

## 3. Detailed Feature Specifications

### 3.1 Resident-Facing Features (WhatsApp Interface)

1. **Cumulative Dues & Billing**
   * Residents receive a single monthly cumulative bill, itemized with a breakdown (society maintenance fee, utility charges, Hamsayaa SaaS fee).
   * The bill is generated by the Admin each cycle — confirmed, not a fully automatic recurring charge. The Admin is allowed to make changes to resident bills directly.
   * Rates and dues are configured by society Admins on the web dashboard.
   * **Payment Flow:** Manual bank transfer or mobile wallet (JazzCash, EasyPaisa) into the **society's own account** shown on the bill. The resident sends a receipt screenshot/photo to the WhatsApp bot for Admin verification.
   * Hamsayaa does not operate the collection account. Hamsayaa bills the society separately and cumulatively each month based on subscribed unit count.

2. **AI Guardrail & Context Filtering**
   * Powered by the **Gemini API** (`gemini-1.5-flash`).
   * Inbound messages pass through a contextual guardrail. If a message is off-topic, spam, or irrelevant to society operations, the AI declines processing, a polite notification is sent, and the prompt is flagged for Admin review on the dashboard.
   * If the bot fails to resolve a valid resident query after **2 attempts**, it auto-generates a ticket tagged `category: needs_human_review`.

3. **Visitor & Vehicle Entry Passes (Token-Optimized)**
   * Resident pre-approves a guest by providing visitor name, CNIC, vehicle plate number, and entry timeframe to the WhatsApp bot.
   * System generates an expiring pass formatted as a compact PDF or image (pre-compiled HTML/Canvas layouts to minimize LLM token overhead).
   * **Delivery:** The generated pass PDF/image is delivered directly to the **resident only** via WhatsApp (resident forwards it to guest).
   * **Gate-side verification — confirmed:** the visitor presents the pass (the PDF/image forwarded to them by the resident) at the gate, and it is checked **visually** — no scanning, no system lookup, since gatekeepers have no system access. The pass includes a human-readable `pass_code` printed on it, but there is no gate-facing scanner or lookup interface.
   * **Data handling:** Visitor **CNIC** is collected and stored as part of every pass. CNIC data is **automatically purged after 30 days**.

4. **Complaint Registration & Management**
   * Supports text input in Phase 1; voice-note transcription via Gemini in Phase 2 (Gemini native audio input is confirmed supported).
   * Extracts complaint category, unit number, description, and attached photos; returns a unique tracking ticket ID.

5. **Society Polls & Digital Voting**
   * Residents cast votes directly inside WhatsApp (strictly one vote per unit).
   * Once poll duration expires, the system automatically compiles results into a static Excel/PDF summary.
   * **Resident visibility — confirmed:** residents are sent the same shared results file/link via WhatsApp, with their own flat/unit number included in the accompanying message text.
   * The summary is generated without an LLM call to keep token cost near zero.

6. **Amenities Information & Facility Queries**
   * Informational lookups for community rules, gym/hall timings, and schedules (Phase 1); facility slot reservation workflows (Phase 2).
   * Amenity details (timings, rules, capacity, bookable flag) are maintained by Admin and must be editable without a code change.

### 3.2 Dashboard Features (Admin)

1. **Manual Account Suspension (Dues Overdue Control)**
   * Account suspension is strictly **manual (Admin-triggered)**. When a resident has overdue payments, the dashboard alerts the Admin, who can manually toggle account suspension (`is_blocked`).
   * When suspended, the bot blocks feature usage and strictly responds with payment resolution instructions and account details.

2. **Bulk Resident & Registered Vehicle Onboarding (Excel / CSV)**
   * Admins can upload resident rosters and registered vehicle databases in bulk via Excel/CSV files, or add entries manually through dashboard forms.

3. **Vehicle Entry Logging & Overstay Tracking**
   * Admins log daily vehicle entries and exits manually, via Excel import, or (Phase 2) automated entrance camera captures.
   * **Confirmed scope of the overstay check:** it applies **only to unregistered vehicles** — i.e. vehicles not in `registered_vehicles`, which are assumed to be visitors who entered through a registered entry pass. **Registered resident vehicles are never subject to an overstay alert** and are excluded from this check entirely, since residents' own vehicles are expected to stay indefinitely.
   * If an unregistered vehicle is still on the premises (per camera/log data) after its associated visitor pass's validity window has ended, an **immediate** overstay alert triggers on the real-time Admin dashboard. There is **no grace period** — the alert fires as soon as the pass expires and the vehicle has not exited.
   * The overstay mechanism is a per-society-configurable feature, but the default grace is **0 minutes** (immediate flagging).
   * **Vehicle logging source for Phase 1:** Manual entry and Excel import only. Camera/ANPR deferred to Phase 2.

4. **Real-Time Operational Dashboard**
   * Live dashboard displaying open tickets, flagged messages, overdue bills, overstay alerts, and active visitor passes.

5. **Financial Ledger & Expense Tracking**
   * Track collected maintenance dues alongside logged society expenses (repairs, utilities, staff salaries) for complete income-vs-expense transparency.
   * **Resident invoices** are editable by the Admin (amounts, due dates, and line items can be updated directly).
   * **Society expense entries** (`expenses` table) are append-only once recorded — status fields may transition but the underlying amount/vendor/date fields are not editable after creation. Corrections require a reversing entry, not an in-place edit.

6. **Employee Directory**
   * Gate staff and other non-system-user employees (security guards, maintenance staff) are listed here with name, role, contact info, and shift assignment.
   * This is a read/write record maintained by Admin — **not an account the employee logs into.** Employees have no WhatsApp bot or dashboard access of any kind (see Section 2).
   * Staff attendance/payroll tracking remains explicitly out of scope (Section 5).

7. **Asset Directory & Maintenance Logs**
   * All society assets (generators, lifts, water pumps, etc.) tracked with install date and service history.
   * Predictive maintenance nudges: system auto-alerts Admins ahead of AMC expiry or scheduled service dates, not only after a complaint is filed. *(Phase 2 — building on Phase 1's basic CRUD.)*

## 4. Scope & Roadmap

* **Phase 1 (MVP Pilot):** WhatsApp cumulative bill queries, Gemini API context filtering, manual Admin block control, Excel bulk import for residents & registered vehicles, token-optimized visitor pass PDF/image generator, manual/Excel vehicle logging with immediate overstay alerts, single real-time dashboard, employee & asset directories (basic CRUD, no predictive alerts yet), amenity information lookup (no booking).
* **Phase 2:** Automated camera feed ingestion for vehicle entry/exit, Gemini voice-note transcription, amenity reservation conflict engine, predictive asset maintenance alerts, multi-language support (Urdu/Roman Urdu).
* **Phase 3:** Scaling multi-tenant infrastructure and advanced reporting.

---

## 5. Explicitly Out of Scope

Do not implement or reintroduce the following features:
* Panic / SOS alert buttons.
* Staff attendance or payroll tracking modules.
* Gatekeeper / security guard dashboard or app logins.
* Automated payment gateway integrations (Safepay, JazzCash API, EasyPaisa API).
* Automatic account blocking upon payment due date (must remain manual Admin trigger).
* Direct automated pass dispatch to guest phone numbers (passes go to residents only).
* **Any gate-facing scanning, lookup, or code-verification interface** — the `pass_code` is human-readable only; there is no system access at the gate.
* Management Committee role or separate dashboard views.

## 7. Business Logic & Confirmed Architecture Rules

1. **AI Model Engine:** Standardized on Gemini API (`gemini-1.5-flash`) for low latency and token efficiency. Native audio input for voice-note transcription is confirmed supported for Phase 2.
2. **Pass Layout:** Pre-compiled HTML/Canvas rendered to PDF/Image, sent directly to resident via WhatsApp. `pass_code` is printed on the pass for human visual verification only.
3. **Vehicle Registration Strategy:** Manual registration and Excel batch import for both resident vehicles and daily entry logs at launch; camera/ANPR deferred to Phase 2.
4. **Poll Summary Distribution:** Static Excel/PDF report auto-compiled and emailed upon poll expiration. One shared file is distributed to all residents via WhatsApp with personalized message text.
5. **Financial Ledger Integrity:** Society `expenses` are append-only for amount/vendor/date fields once recorded; status transitions only. Resident `invoices` are editable by the Admin.
6. **Visitor CNIC Retention:** Automatically purged after 30 days.
7. **Overstay Alert:** Immediate (0-minute grace) for unregistered vehicles past their visitor pass expiry.
8. **Backend Framework:** Python (FastAPI) confirmed.
9. **Dashboard Auth:** Supabase Auth with single `admin` role.
